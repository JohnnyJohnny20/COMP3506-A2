Task 2.5: The UQ Nephilim Labyrinth

I used Claude to review my approach, trace my code for bugs, and suggest test cases.
Claude did not write any code; the implementation is my own.

My initial plan, before any AI input: query every node once with the full node set
to get its longest-path length, so the largest value is the path length and the
values count down along the path. To handle ties (several nodes with the same
value), I planned to re-query with half of the candidate nodes removed, binary-search
style. I estimated the cost as L * log2(candidates) < N, so the total would stay
under 2N. I also wrote the initial loop making the N queries.

*I did, off my own analysis, switch away from binary search for duplicates despite some AI interaction about it

Prompt: [Pasted plan]. Is it a good approach to find duplicates with a binary search
style re-query?
Response: Said the first step was sound and that duplicates were the real problem.
Claimed binary search wouldn't fit the 2n tier.
Prompt: I disagree, wouldn't it be this bound (L * log2(candidates))
Response: corrected itself and explained why the total stays
under 2n.

Prompt: Is an int[][] or a hash structure better for the buckets?
Response: Said either works and that dense integer keys suit arrays. I chose a
list of lists indexed by query value.

Prompt: [Pasted code]. I'm getting NoSuchElementException / an out of range vertex.
Response: Pointed out the bucket count was off by one, the walk started at n rather
than the longest path length, prev was a bucket number rather than a node id, the
test array had stale slots, and the final array was sized n. Pointed me to the
docstring to show query counts vertices, so a return of 0 never happens.

Prompt: Isn't the two-vertex check safe if a successor is a dead end?
Response: Gave the general argument (successor values are at most k-1, and at least
one equals k-1), which rules out dead ends and indirect routes.
